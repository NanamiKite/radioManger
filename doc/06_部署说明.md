# 部署说明

## 部署模式对比

| 方式 | 网页入口 | 数据库与后端 | 适用条件 |
| --- | --- | --- | --- |
| 源码本地运行 | Vite，默认 5173 | 本机 FastAPI 8000 + SQLite | 已安装 Python、Node.js |
| Docker 服务器 | Nginx 80 | FastAPI + MySQL + Redis | 多用户、局域网或云服务器 |
| Windows Web 本地包 | 浏览器访问 8000 | 包内 Python + SQLite | 使用打包后的 `start.bat` |
| Windows pywebview 包 | WebView2 窗口访问本机 8000 | 后端子进程 + SQLite | 需要 pywebview 依赖及 WebView2 |
| Electron | 加载前端页面 | Python 后端需另行提供 | 仓库仅配置前端壳打包 |
| Android 浏览器/容器 | 服务器网页或 Capacitor 资源 | 远程后端 | 需要可访问的服务器；容器还需配置 API 路由 |

后端模式通过配置选择，不能在前端设置页切换。本文从项目根目录开始说明；命令中的密码、密钥、绝对路径和域名需要替换为部署值。

## 1. 纯本地部署

### 1.1 前置要求

源码环境可按仓库容器和打包脚本使用 Python 3.12、Node.js 22，以及 npm。初次安装依赖需要网络；日志数据库读写在本机完成。QRZ、DX Cluster 和在线地图底图仍需要网络。

### 1.2 配置与脚本启动

先创建 `backend/.env`。已有配置时编辑原文件，保留数据库路径与 JWT 密钥。

```dotenv
DATABASE_MODE=sqlite
SQLITE_URL=sqlite:////absolute/path/radioManger/backend/radiomanager.db
SQLITE_PATH=/absolute/path/radioManger/backend/radiomanager.db
SECRET_KEY=replace-with-a-random-secret
ENVIRONMENT=development
DEBUG=true
ENABLE_TEST_ACCOUNT=false
CORS_ORIGINS=["http://localhost:5173"]
```

Unix SQLite 绝对路径在 `sqlite:` 后有四个 `/`。Windows 示例为 `SQLITE_URL=sqlite:///C:/RadioManager/backend/radiomanager.db`、`SQLITE_PATH=C:/RadioManager/backend/radiomanager.db`。路径中的目录须已存在；两个变量应指向同一个文件。

从 Python 生成密钥后填入 `.env`：

```bash
python3 -c 'import secrets; print(secrets.token_hex(32))'
```

配置完成后，在项目根目录运行：

```bash
./start-local.sh
```

该脚本创建或激活 `backend/venv`、初始化数据库，再启动 FastAPI 和 Vite。首次创建虚拟环境时安装后端依赖，缺少前端依赖目录时运行 npm 安装。脚本读取现有配置，不会强制覆盖 `DATABASE_MODE`，也没有实现 `--build` 参数。

### 1.3 手动启动

后端终端：

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
python -m app.scripts.init_db
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

前端终端：

```bash
cd frontend
npm ci
npm run dev
```

使用绝对 SQLite 路径可让初始化和运行进程始终使用同一个文件。日后启动后端时，也应从 `backend/` 运行，以读取同一 `.env`。

### 1.4 访问

- 网页：[http://localhost:5173](http://localhost:5173)
- 健康检查：[http://localhost:8000/health](http://localhost:8000/health)
- 交互 API 文档：[http://localhost:8000/docs](http://localhost:8000/docs)，仅 `DEBUG=true` 时开放

默认不创建测试账号，在注册页创建账户即可。登录后先创建台站和位置；第一个位置会自动激活。

### 1.5 环境变量配置

[`config.py`](../backend/app/config.py) 从进程环境和当前工作目录的 `.env` 读取设置，环境变量优先，变量名区分大小写。

| 变量 | 默认值或用途 |
| --- | --- |
| `DATABASE_MODE` | `sqlite`；服务器用 `mysql` |
| `SQLITE_URL` | 默认 `sqlite:///./radiomanager.db`；实际数据库连接 |
| `SQLITE_PATH` | 默认 `./radiomanager.db`；设置页显示路径 |
| `DATABASE_URL` | MySQL 必填，如 `mysql+pymysql://用户:密码@主机:3306/数据库` |
| `SECRET_KEY` | 生产环境必须非空，使用持久随机值 |
| `ENVIRONMENT` | 默认 `production` |
| `DEBUG` | 默认 `false`，控制 `/docs` 与 `/redoc` |
| `CORS_ORIGINS` | JSON 数组，如 `["https://radio.example.com"]` |
| `REDIS_URL` | 默认 `redis://localhost:6379` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | 默认 10080，即 7 天 |
| `REFRESH_TOKEN_EXPIRE_DAYS` | 默认 30；没有刷新端点 |
| `ADMIN_USERNAME/PASSWORD/EMAIL` | MySQL 显式初始化时使用；密码为空则跳过创建 |
| `ENABLE_TEST_ACCOUNT` | 默认 `false`；仅控制 SQLite 初始化脚本的测试账户创建 |
| `TEST_ACCOUNT_USERNAME/PASSWORD/EMAIL` | SQLite 测试账户及发布入口使用的账户配置 |
| `QRZ_USERNAME/PASSWORD` | QRZ XML 查询凭据 |
| `UDP_WSJTX_PORT/UDP_N1MM_PORT` | 默认 2237 / 12060 |
| `UDP_ENABLED` | 已定义，但不触发自动监听 |
| `GITHUB_TOKEN`、`SMTP_*` | 同步与邮件的预留配置，不表示功能已经接通 |

`backend/.env.example` 可用于查找配置项，其中的示例凭据需要替换；`CORS_ORIGINS` 应按本文改为 JSON 数组，不能使用逗号分隔字符串。导入路由实际限制 50 MiB，不使用配置中的 `MAX_UPLOAD_SIZE` 值。

## 2. 局域网部署

### 2.1 Docker 全栈部署

[`docker-compose.yml`](../docker-compose.yml) 启动 MySQL、Redis、FastAPI 和前端 Nginx。Compose 的变量替换读取**项目根目录 `.env`**，它与源码后端使用的 `backend/.env` 是不同文件。

在根目录 `.env` 填入以下变量，替换所有占位值。数据库密码会进入连接 URL，使用不含 URL 保留字符的随机值，或正确编码。

```dotenv
MYSQL_ROOT_PASSWORD=replace-with-a-random-root-password
MYSQL_PASSWORD=replace-with-a-random-db-password
SECRET_KEY=replace-with-a-random-jwt-secret
ADMIN_USERNAME=admin
ADMIN_PASSWORD=replace-with-a-random-admin-password
ADMIN_EMAIL=admin@example.com
```

前端依赖 `/health` 识别服务器模式。构建前，在 [`frontend/nginx.conf`](../frontend/nginx.conf) 的 `server` 块内补充健康检查转发：

```nginx
location = /health {
    proxy_pass http://backend:8000;
    proxy_set_header Host $host;
}
```

现有配置已包含 `/api`、DX Cluster/UDP WebSocket 和 SPA 回退。Nginx 的上传大小限制需要与导入需求一致；如需允许最大 50 MiB 文件及 multipart 开销，可在该 `server` 块设置 `client_max_body_size 51m;`。默认 Nginx 限制可能先于 API 拒绝文件。

配置好后，在项目根目录运行：

```bash
docker compose up -d --build
docker compose exec backend python -m app.scripts.init_db
docker compose ps
curl http://localhost:8000/health
```

后端镜像启动命令直接运行 Uvicorn，不执行管理员初始化；首次部署的第二条命令不可省略。已有同用户名账户时，初始化不会覆盖其密码。

浏览器访问 `http://服务器IP/`，使用配置的管理员登录。MySQL 与 Redis 数据分别存入 `mysql_data`、`redis_data` 卷。停止服务使用 `docker compose down`；不要在需保留数据时添加 `-v`。

仓库 Compose 同时发布 80、8000、3306、6379 端口。普通浏览器只需要前端入口；部署方应按网络范围限制数据库、Redis 和后端端口，或调整端口映射。

### 2.2 前后端分机部署

客户端依赖同源 `/api/v1`、`/health` 和 WebSocket 路径。只设置 CORS 或启动脚本中的 API 地址变量，不会更改请求目标。

开发时，在前端机器的 `vite.config.ts` 中把 `/api` 和 `/health` 的 `target` 都改为实际后端地址，保留 `/api` 的 `ws:true`，再运行：

```bash
cd frontend
npm ci
npm run dev -- --host 0.0.0.0
```

后端监听允许其他机器访问的地址：

```bash
cd backend
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

正式部署时，构建 `frontend/dist` 并由 Nginx 托管，通过同源代理转发三类路径。Vite 开发服务器只用于开发环境。

### 2.3 数据库选择

SQLite 使用本机文件，适合个人日志；MySQL 使用独立数据库服务，并启用服务器管理接口。SQLite 模式仍有用户认证，不代表无账号、无权限隔离。

数据库模式切换只改变连接目标，不迁移旧数据。迁移前应备份数据库；ADI 导入导出只覆盖部分字段，不能作为完整迁移方式。

## 2.4 服务器部署模式（MySQL + Redis）

非容器运行时，在 `backend/.env` 设置：

```dotenv
DATABASE_MODE=mysql
DATABASE_URL=mysql+pymysql://radiomanager:replace-password@127.0.0.1:3306/radiomanager
REDIS_URL=redis://127.0.0.1:6379/0
SECRET_KEY=replace-with-a-random-secret
ADMIN_USERNAME=admin
ADMIN_PASSWORD=replace-with-a-random-admin-password
ADMIN_EMAIL=admin@example.com
ENVIRONMENT=production
DEBUG=false
ENABLE_TEST_ACCOUNT=false
CORS_ORIGINS=["https://radio.example.com"]
```

先创建 MySQL 数据库及应用用户并授予该库权限，再从 `backend/` 执行初始化。数据库创建可使用 `utf8mb4` 字符集。根目录 `init-db.sh` 使用固定示例凭据，不应直接用于正式凭据管理。

MySQL 模式启用管理员路由、登录会话、操作审计和令牌黑名单。Redis 初始化不可用时，黑名单回退进程内存；重启或不同 worker 之间无法保留这种撤销状态。后端默认未提供多进程共享的 DX Cluster/UDP 管理器，应使用单 worker。

## 3. 云服务器部署

### 3.1 运行结构

云部署复用服务器模式，域名和 TLS 由入口代理提供。可以在已启动的 Compose 前端之外配置 TLS 网关，或直接由宿主机 Nginx 托管静态构建。对外网页和 API 保持同源。

### 3.2 静态前端与反向代理

构建前端：

```bash
cd frontend
npm ci
npm run build
```

将 `dist/` 部署到静态目录，例如 `/var/www/radiomanager`。下面的配置假定后端运行在同一主机的 `127.0.0.1:8000`；证书和目录由部署方准备：

```nginx
server {
    listen 80;
    server_name radio.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name radio.example.com;
    ssl_certificate /etc/ssl/radiomanager/fullchain.pem;
    ssl_certificate_key /etc/ssl/radiomanager/privkey.pem;

    root /var/www/radiomanager;
    index index.html;
    client_max_body_size 51m;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 180s;
    }

    location = /health {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }

    location ~ ^/api/v1/(dxcluster|udp)/ws$ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 86400s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

域名使用 HTTPS 后，前端自动使用 `wss` 连接 WebSocket。代理访问日志不宜记录含 token 的 WebSocket 查询参数。

仓库根目录的 `nginx.conf` 是另一种入口示例：它把网页代理到 5173，而不是直接托管 `dist/`；同样需要补充 `/health`。不要在同一个部署中混淆开发服务器代理与静态资源托管方式。

### 3.3 运行维护

通过进程管理器或容器保持后端运行，从固定工作目录读取 `.env`。升级前保存数据库、配置与旧版本产物，在副本验证升级，再更新服务。`create_all` 不会升级已有列结构。

健康检查必须读取 JSON 中的 `status` 和 `subsystems`。API 在数据库或 Redis 异常时仍返回 HTTP 200，容器现有健康检查只检查 HTTP 可达，不保证子系统正常。

## 4. Windows 部署

### 4.1 源码本地运行

配置 `backend/.env`，SQLite 使用 Windows 绝对路径。PowerShell 后端命令：

```powershell
cd backend
py -3.12 -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m app.scripts.init_db
python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

另一个终端在 `frontend/` 执行 `npm ci` 和 `npm run dev`。`start-windows-local.bat` 也用于启动源码前后端，它最终运行 Vite，不是 Electron 桌面安装包。

### 4.2 Web 本地发布包

`build-win64-v2.6.0.sh` 生成包含 Python、前端静态资源和后端的 Windows 本地包。构建前先在 `frontend/` 安装依赖，再从项目根目录运行：

```bash
bash build-win64-v2.6.0.sh
```

脚本需要下载运行时和 Windows wheels，并使用 `pip`、`wget`、`unzip` 等工具；它会重建同名输出目录。版本名与输出目录以脚本为准。

使用包时从解压目录运行 `start.bat`，浏览器访问 `http://localhost:8000`。`release_server.py` 挂载 `backend/frontend_dist`，首次创建 `TEST_ACCOUNT_*` 指定的账户；它不受 `ENABLE_TEST_ACCOUNT` 开关限制。脚本生成的默认账户是 `admin/admin123`，使用前应调整包根目录 `.env` 的密钥和账户配置。已有账户不会因修改初始密码配置而自动更新。

该包的 SQLite 默认位于解压目录根部，配置文件也是包根目录 `.env`。它与源码运行的 `backend/.env` 不是同一个运行入口。

`build-win64-web.sh`、`build_release.sh` 是其他版本的包装脚本，不能仅凭文件名认定与当前包行为一致。

### 4.3 桌面窗口与 Electron

`build-win64-desktop.sh` 使用 `desktop_launcher.py` 和 pywebview/Edge WebView2，在 Windows 窗口内打开本机 HTTP 页面，并在窗口关闭时结束后端进程。它与 Electron 是不同入口。

Electron 命令在 `frontend/` 运行：

```bash
npm run electron
npm run electron:win
npm run electron:win-portable
npm run electron:linux
npm run electron:mac
```

Electron 优先加载 `dist/index.html`，没有构建目录时加载本地 5173。打包配置只包含前端与 Electron 文件，`extraResources` 为空；主进程不会启动 Python 后端。现有相对 API、WebSocket 和 History 路由依赖 HTTP 服务，不能把前端壳构建成功等同于可直接使用的完整本地桌面应用。

`start-windows-web.bat` 中输入的 `RADIOMANAGER_API_URL` 没有被现有客户端读取；远程使用应配置同源代理或直接访问服务器网页。

## 5. Android 部署

### 5.1 浏览器与主屏幕入口

手机可通过浏览器访问服务器网页。`public/manifest.json` 和图标提供主屏幕显示信息；仓库没有 Service Worker 或离线资源缓存实现，不能承诺完整 PWA 安装能力或离线网页运行。

### 5.2 Capacitor APK 打包

仓库已有 `capacitor.config.ts`，但未包含生成的 `frontend/android/` 工程。安装依赖后，首次添加平台可运行：

```bash
cd frontend
npm ci
npm run build
npx cap add android
npm run android:sync
npm run android:open
```

已有配置时无需重复 `cap init`。安装 Android 构建工具并配置好网络入口后，可运行：

```bash
npm run android:build
```

脚本执行 `assembleDebug`，产物为 `frontend/android/app/build/outputs/apk/debug/app-debug.apk`，不是签名发布包。

### 5.3 网络配置

Capacitor 配置使用 `webDir=dist`、HTTPS scheme，并关闭明文流量。页面仍使用同源 `/api/v1` 和 `/health`，仅设置允许导航的主机不会指定 API 后端；需要为容器明确配置网页服务器或适配请求地址后再使用。Android 包不包含 Python 后端或本地数据库服务。

## 6. 数据库初始化

推荐入口为 `python -m app.scripts.init_db`：

1. 新数据库通过 ORM 创建所有表，再尝试标记 Alembic head。
2. 已有表时尝试执行迁移；当前脚本在迁移失败后还可能尝试 stamp，因此版本标记不能单独证明结构已升级。
3. MySQL 模式读取 `ADMIN_*` 创建管理员；SQLite 仅在 `ENABLE_TEST_ACCOUNT=true` 时创建测试账户。

当前唯一迁移仅调整 `users.role`，不包含从空库建表。已有数据升级前先备份并检查实际迁移，不要把 stamp 当作结构修复。

手动创建管理员可在 `backend/` 配置 `ADMIN_USERNAME`、`ADMIN_PASSWORD`、`ADMIN_EMAIL` 后运行：

```bash
python -m app.scripts.create_admin
```

该脚本会输出初始凭据，应在受控终端执行。普通应用入口 `app.main` 自动建表，但不自动创建账户；发布入口 `release_server.py` 有单独的账户创建逻辑。

### 备份与恢复

SQLite 使用 WAL，运行中只复制 `.db` 可能遗漏未合并数据。可使用 Python 标准库在线备份，路径替换为实际值：

```python
import sqlite3

with sqlite3.connect("/absolute/path/radiomanager.db") as source:
    with sqlite3.connect("/absolute/path/backup.db") as target:
        source.backup(target)
```

也可以正常停止所有写入进程后做离线备份。恢复时先停止应用，保存现有文件，再替换为备份并检查日志数与抽样记录。MySQL 使用一致性数据库备份工具，保存并验证备份文件；不要直接复制运行中的数据库数据目录。

ADI 导出不包含全部数据库字段和关系，不能替代完整备份。GitHub 同步仍为预留实现。

## 7. 启动脚本说明

| 脚本 | 实际用途 |
| --- | --- |
| `start-local.sh` | 初始化后启动 Vite 与 Uvicorn，读取现有配置 |
| `start-dev.sh` | 同上；以 shell 中的 `DATABASE_MODE` 选择模式，未设时导出 `sqlite` |
| `start-server-mode.sh` | 本机 MySQL 调试，会覆盖 `backend/.env`，含固定测试凭据 |
| `start-prod.sh` | 包装旧版 `docker-compose` 命令；实际网页端口以 Compose 为准 |
| `start-windows-local.bat` | Windows 源码依赖安装、初始化与 Vite/Uvicorn 启动 |
| `start-windows-web.bat` | 前端/Electron 选项；API 地址输入未接入客户端 |
| 发布包 `start.bat` | 运行 `release_server.py`，同源提供网页与 API |

## 8. 常见问题

| 现象 | 检查与处理 |
| --- | --- |
| 无法登录初始账户 | 确认是否执行账户初始化；默认源码环境没有测试账户 |
| 启动时提示空密钥 | 在实际进程读取的 `.env` 设置持久 `SECRET_KEY` |
| 初始化后看不到数据 | 检查工作目录与 SQLite 绝对路径，保证初始化和服务连接同一文件 |
| 设置页模式不正确、管理入口不显示 | 从浏览器同源访问 `/health`，确认代理返回 JSON，而不是 SPA 页面 |
| API 可用但实时数据不更新 | 检查 WebSocket Upgrade 转发，HTTPS 页面须使用 `wss` |
| 导入出现 413 | 同时检查 Nginx 上传限制和 API 的 50 MiB 限制 |
| 页面刷新出现 404 | 为 History 路由配置 `index.html` 回退，API 路径单独代理 |
| 健康检查 200 但服务异常 | 读取 `status` 和 `subsystems`，不能只看 HTTP 状态 |
| UDP 没有数据 | 数据发往后端主机，确认监听已启动并允许目标 UDP 端口 |

Docker Compose 未映射 UDP 端口。容器需要接收外部广播时，另外映射使用的端口，例如 `2237:2237/udp` 和 `12060:12060/udp`；收到广播也不代表日志已经保存，见[UDP API](03_API设计说明.md#十五udp-模块apiv1udp)。
