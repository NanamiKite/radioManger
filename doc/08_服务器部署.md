# 服务器部署

适用于多人访问的局域网与云服务器场景。单机使用见[本地部署](07_本地部署.md)；环境变量含义见[环境变量配置](07_本地部署.md#环境变量配置)。

## 1. 局域网部署

### 1.1 Docker 全栈部署

[`docker-compose.yml`](../docker-compose.yml) 启动 MySQL、FastAPI 和前端 Nginx，不再依赖 Redis。Compose 变量读取**项目根目录 `.env`**，与源码后端的 `backend/.env` 不同。

前端镜像固定为 `nginx:1.31.9-alpine`，包含 2026-11-18 公布的 HTTP/2、TLS、resolver 等安全修复，见 [Nginx 官方安全公告](https://nginx.org/en/security_advisories.html)。避免使用旧缓存或浮动 `nginx:alpine` 标签。

在根目录 `.env` 填入以下变量，替换所有占位值。数据库密码会进入连接 URL，使用不含 URL 保留字符的随机值，或正确编码。

```dotenv
MYSQL_ROOT_PASSWORD=replace-with-a-random-root-password
MYSQL_PASSWORD=replace-with-a-random-db-password
SECRET_KEY=<用 secrets.token_hex(32) 生成的随机密钥>
ADMIN_USERNAME=admin
ADMIN_PASSWORD=replace-with-a-random-admin-password
ADMIN_EMAIL=admin@example.com
```

前端 Nginx 已包含 `/api`、`/health`、DX/UDP WebSocket 转发、SPA 回退与 `client_max_body_size 51m`。边缘代理覆盖 `X-Forwarded-For`，后端只信任 ASGI 服务器解析后的客户端地址，不自行读取请求头。

配置好后，在项目根目录运行：

```bash
docker compose build --pull frontend
docker compose up -d --build
docker compose logs backend
docker compose ps
curl http://localhost/health
```

后端先执行迁移，再按显式 `ADMIN_PASSWORD` 创建管理员，最后启动单 worker。未设置管理员密码时不创建管理员；可执行 `docker compose exec backend python -m app.scripts.create_admin` 隐藏输入密码。已有同用户名的普通用户不会被自动提权；已有管理员密码不会被覆盖。

浏览器访问 `http://服务器IP/`。MySQL 数据存入 `mysql_data` 卷；停止使用 `docker compose down`，需保留数据时不要加 `-v`。默认仅发布 80 端口；MySQL 和后端只在容器网络中可达，不发布 3306、6379 或 8000。

### 1.2 前后端分机部署

客户端使用同源 `/api/v1`、`/health` 和 WebSocket 路径，请求目标由代理配置决定。

开发时，在前端机器的 `vite.config.ts` 中把 `/api` 和 `/health` 的 `target` 都改为实际后端地址，保留 `/api` 的 `ws:true`，再运行：

```bash
cd frontend
npm ci
npm run dev -- --host 0.0.0.0
```

后端监听允许其他机器访问的地址：

```bash
cd backend
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 1
```

正式部署时，构建 `frontend/dist` 并由 Nginx 托管，通过同源代理转发三类路径。Vite 开发服务器只用于开发环境。

### 1.3 数据库选择

SQLite 使用本机文件，适合个人日志；MySQL 使用独立数据库服务，并启用服务器管理接口。SQLite 模式同样有用户认证和权限隔离。

数据库模式切换只改变连接目标，不迁移旧数据；切换前先备份数据库。ADI 导入导出只覆盖部分字段，不适合作为完整迁移方式。

## 2. 服务器部署模式（MySQL）

非容器运行时，在 `backend/.env` 设置：

```dotenv
DATABASE_MODE=mysql
DATABASE_URL=mysql+pymysql://radiomanager:replace-password@127.0.0.1:3306/radiomanager
SECRET_KEY=<用 secrets.token_hex(32) 生成的随机密钥>
ADMIN_USERNAME=admin
ADMIN_PASSWORD=replace-with-a-random-admin-password
ADMIN_EMAIL=admin@example.com
ENVIRONMENT=production
DEBUG=false
CORS_ORIGINS=["https://radio.example.com"]
```

先创建 MySQL 数据库及应用用户并授予该库权限，再从 `backend/` 执行迁移和显式管理员创建。数据库可使用 `utf8mb4` 字符集。`init-db.sh` 从必填环境变量读取建库凭据，不附带固定密码。

MySQL 模式启用管理员路由和审计；两种模式都用 SQL 会话校验及撤销令牌。主机级 DX/UDP 和限流仍使用单进程状态，部署必须为单 worker。服务器模式只有管理员能切换 DX 节点或启动 UDP；UDP 只交付给启动者。

## 3. 云服务器部署

### 3.1 运行结构

云部署复用服务器模式，域名和 TLS 由入口代理提供。可以在已启动的 Compose 前端之外配置 TLS 网关，或直接由宿主机 Nginx 托管静态构建。对外网页和 API 保持同源。

宿主机 Nginx 也必须升级到 **1.31.9+** 或稳定分支 **1.30.7+**；发行版回补包需核对厂商公告。宿主机软件需单独升级。根目录示例启用 HTTP/2/TLS 1.3，未修补版本可能受 CVE-2026-123007、CVE-2026-123633、CVE-2026-118899 影响。无法立即升级时，可临时关闭受影响协议作为缓解。

### 3.2 静态前端与反向代理

构建前端：

```bash
cd frontend
npm ci
npm run build
```

将 `dist/` 部署到静态目录，例如 `/var/www/radiomanager`。下面的配置假定后端运行在同一主机的 `127.0.0.1:8000`；证书和目录由部署方准备：

```nginx
server {
    listen 80;
    server_name radio.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name radio.example.com;
    ssl_certificate /etc/ssl/radiomanager/fullchain.pem;
    ssl_certificate_key /etc/ssl/radiomanager/privkey.pem;

    root /var/www/radiomanager;
    index index.html;
    client_max_body_size 51m;

    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 180s;
    }

    location = /health {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
    }

    location ~ ^/api/v1/(dxcluster|udp)/ws$ {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 86400s;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

HTTPS 页面自动使用 `wss`。WebSocket 连接后首条消息认证，不在 URL 中传 JWT。自定义 DX 节点需在服务端 `DX_CLUSTER_NODES` 配置，普通用户不能指定任意出站地址。

仓库根目录 `nginx.conf` 现在直接托管 `/var/www/radiomanager/dist` 并代理 API、健康检查和 WebSocket。生产不使用 Vite 开发服务器。

### 3.3 运行维护

通过进程管理器或容器保持后端运行，从固定目录读取 `.env`。升级前保存数据库、配置和旧产物，在副本执行迁移；旧库无版本标记时按[旧库接管说明](10_初始化备份与常见问题.md#1-数据库初始化)显式校验。删除旧配置中的 `REDIS_URL`、`REFRESH_TOKEN_EXPIRE_DAYS`，设置 `WORKERS=1`。

健康检查正常返回 200/`ok`，数据库失败返回 503/`degraded`。Docker healthcheck 同时检查 HTTP 与 JSON 状态。已有令牌需重新登录；初始化与备份步骤见[初始化备份与常见问题](10_初始化备份与常见问题.md)。

安全升级需重建并重新创建前端容器，不能只重启旧容器：

```bash
docker compose build --pull frontend
docker compose up -d --no-deps frontend
docker compose exec frontend nginx -v
```

最后一条用于核对实际运行的 Nginx 版本。当前容器配置未启用 HTTP/2、HTTP/3 或 TLS；外置 TLS 网关和宿主机 Nginx 需分别核实。

## 4. CI 服务端验证

Actions 的 **Manual target validation** 选择 `server` 后，才在一次性 Linux runner 构建镜像、启动独立 Compose 项目并验证实际 HTTP/WebSocket 和重启持久化。随机凭据、项目卷和临时端口与生产隔离；报告记录实际 Nginx 版本，退出后清理验证资源。

普通 PR 不自动启动完整 Compose；涉及共享后端时可单独运行 MySQL 测试。该流程只验证候选镜像，不推送镜像或连接生产服务器。使用方式见[GitHub Actions](12_测试设计与验收.md#github-actions)。
